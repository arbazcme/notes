# LEC 14 - Graceful Shutdown

# The Problem

Imagine a server is processing a critical payment when a new deployment starts.

If the server stops immediately,

possible problems include

- Payment processed twice
- Payment lost
- Partial database updates
- Data corruption
- Poor user experience

Instead of stopping abruptly,

the server should finish its current work before shutting down.

This is called **Graceful Shutdown**.

---

# What is Graceful Shutdown?

Graceful Shutdown is the process of **stopping an application safely**.

Instead of

```text
Stop Immediately
```

the server

- Stops accepting new requests
- Finishes ongoing requests
- Cleans up resources
- Exits safely

---

# Why is it Important?

Benefits

- Prevents data corruption
- Avoids duplicate transactions
- Prevents incomplete requests
- Releases resources properly
- Makes deployments safer
- Improves reliability

---

# Process Lifecycle

Every backend application runs as an **Operating System Process**.

Every process has a lifecycle.

```text
Start

↓

Running

↓

Shutdown

↓

Exit
```

Graceful shutdown handles the final stage correctly.

---

# How Does the OS Tell a Process to Stop?

Operating systems communicate with processes using **Signals**.

Think of signals as messages from the OS.

```text
Operating System

↓

Signal

↓

Application

↓

Handle Shutdown
```

---

# Important Signals

## SIGTERM (Terminate)

The normal shutdown signal.

Meaning

> "Please finish your work and exit."

Used by

- Kubernetes
- Docker
- PM2
- systemd
- Deployment systems

The application gets time to clean up before exiting.

---

## SIGINT (Interrupt)

Usually generated by

```text
Ctrl + C
```

Used mostly during development.

Handled almost the same way as SIGTERM.

---

## SIGKILL (Kill)

Forces the application to stop immediately.

Properties

- Cannot be caught
- Cannot be ignored
- No cleanup happens

Equivalent to

```text
Pulling the power cable
```

instead of shutting down normally.

---

# SIGTERM vs SIGKILL

| SIGTERM | SIGKILL |
|----------|----------|
| Graceful | Immediate |
| Cleanup allowed | No cleanup |
| Finish requests | Requests aborted |
| Preferred | Last resort |

---

# Graceful Shutdown Workflow

```text
Receive Shutdown Signal

↓

Stop Accepting New Requests

↓

Finish Existing Requests

↓

Release Resources

↓

Exit Process
```

---

# Step 1 - Stop Accepting New Requests

The server should immediately stop accepting new client requests.

Existing requests continue,

new requests are rejected or routed to another server.

This prevents additional work during shutdown.

---

# Step 2 - Finish Existing Requests

Requests already being processed are called **In-flight Requests**.

Example

```text
Request Started

↓

Payment Processing

↓

Finish Payment

↓

Return Response

↓

Shutdown
```

Do **not** terminate them halfway.

---

# Connection Draining

This process is called **Connection Draining**.

The server

- Stops accepting new connections
- Waits for active requests to complete
- Closes remaining connections

Think of a restaurant closing.

```text
Stop New Customers

↓

Existing Customers Finish Eating

↓

Restaurant Closes
```

---

# Connection Draining in Different Systems

### HTTP Server

- Stop accepting HTTP requests
- Finish active requests
- Close server

---

### Database

- Finish running queries
- Commit or rollback transactions
- Close database connections

---

### WebSockets

- Notify clients
- Close socket gracefully

---

# Shutdown Timeout

The server cannot wait forever.

A timeout is configured.

Example

```text
30 Seconds
```

Workflow

```text
Shutdown Signal

↓

Wait up to 30 Seconds

↓

Requests Finished?

↓

Yes

↓

Exit

No

↓

Force Shutdown
```

Timeout depends on

- Request duration
- Business requirements
- Deployment strategy

---

# Resource Cleanup

Applications acquire resources while running.

Before exiting,

they must release them.

Common resources

- Database connections
- Redis connections
- Network sockets
- File handles
- Temporary files
- Background workers
- Cache connections

---

# Why Cleanup Matters

Without cleanup

- Memory leaks
- Locked files
- Hanging database connections
- Resource exhaustion
- Incomplete transactions

can occur.

---

# Database Cleanup

Before shutting down

- Finish queries
- Commit completed transactions
- Roll back incomplete transactions
- Close connection pool

Never leave transactions in an inconsistent state.

---

# Cleanup Order

Resources should usually be released in the **reverse order** they were acquired.

Example

```text
Acquire

Database

↓

Redis

↓

Background Workers
```

Shutdown

```text
Background Workers

↓

Redis

↓

Database
```

This avoids dependency issues.

---

# Typical Graceful Shutdown Flow

```text
OS

↓

SIGTERM / SIGINT

↓

Application

↓

Stop New Requests

↓

Finish Existing Requests

↓

Close HTTP Server

↓

Close Database

↓

Close Redis

↓

Stop Background Workers

↓

Exit
```

---

# Where Is It Used?

Graceful shutdown is important during

- Deployments
- Server restarts
- Scaling down
- Container shutdown
- Kubernetes pod termination
- Manual server stop

---

# Production Deployment

During deployment

Old Server

```text
Stop Receiving New Requests

↓

Finish Existing Requests

↓

Shutdown
```

Meanwhile

New Server

```text
Start

↓

Health Check

↓

Receive Traffic
```

This enables **zero-downtime deployments**.

---

# Best Practices

- Handle SIGTERM and SIGINT.
- Stop accepting new requests immediately.
- Finish in-flight requests.
- Configure a reasonable shutdown timeout.
- Commit or roll back transactions.
- Close all external connections.
- Release resources in reverse order.
- Log shutdown events.
- Never rely on SIGKILL for normal shutdowns.
